# WARA 開発ノート｜決済が届くまでと、友人に案内する前のToDo

2026-11-14 時点。対象は `wara.monku.ai` の現行の財布・店舗レジ（v0.3）。サイトは本番公開、取引先は **Solana Devnet（試験用の台帳）**。旧版の `/devnet/`、静的なSites版、オフラインモックは別に扱う。

**現在地：既存の買い手が店舗を選び、1 INAを支払い、店主が着金履歴を読むところまで確認できた。** 次に確かめたいのは、初めての人がスマホで同じ場所までたどり着けるか、数人が同じ時間帯に使っても待ち時間や取りこぼしがないか、の二点。

## 1 INAを払うと、どこで何が起きるか

INAは日本時間の1日につき、財布あたり全地域合計10まで使える枠。残高10 WARAを送るのとは意味が違う。**1 INAを使うと、店に90 WARA、買い手に10 WARAが新しく発行される。** すでに持っているWARAで払う場合は、その発行元のWARAが移動する。

| 順番 | 今回の店舗選択による支払い | 担当 |
| --- | --- | --- |
| 1. 準備 | 買い手が「支払う」から店と金額を選ぶ。ブラウザが台帳の状態と、取引の有効期限に使う直近のブロック情報を読む。 | 買い手の端末 → Solana公式の公開RPC（予備はOnFinalityの公開口） |
| 2. 署名 | 組み込み財布ではWorkerが本人に許された取引か検査して署名する。署名前の有効期限の照合に決済用RPCを使う。 | Cloudflare Worker・D1 → Helius |
| 3. 送信 | 手数料支援を使う場合、Workerが内容を検証し、専用財布で手数料を引き受けて取引を送る。レシートと取引署名を対応づける。 | Workerのリレー → Helius → Solana Devnet。受付記録はD1 |
| 4. 確定 | 日次枠の消費と2人への発行が一つの取引として成立する。途中だけ成功することはない。 | Devnet上のWARAプログラムとトークンプログラム |
| 5. 表示 | 買い手は取引署名で確定を照会。店主の「ありがとうの履歴」は店宛ての確定取引を読み、受取額を表示する。 | 各端末 → 公開RPC。取引リンクはSolana Explorer |

**RPCはアプリが台帳に「読む・送る」と頼むための窓口。** HeliusとOnFinalityは別々の窓口から同じ台帳に接続する。取引の成否を決めるのは台帳で、D1はWARAアプリ用のデータベース。Workerの受付やHTTP 200だけでは着金を証明しない。同じ取引署名で買い手・台帳・店を照合すると、どの段階まで進んだかが分かる。

## 機能と外部サービスの対応

| 機能 | どのサービスを使うか | 何を任せているか |
| --- | --- | --- |
| サイトを開く・APIを呼ぶ | Cloudflare Workers（静的ファイル配信を含む）、CloudflareのDNS・TLS | 画面と同じドメインで会員・店舗・リレーAPIを提供。画面が開けることと、決済が通ることは別々に確認する。 |
| 携帯番号で登録・サインイン | Google Firebase Authentication（電話認証・reCAPTCHA）、Worker、Cloudflare D1 | Googleが番号へのSMS送信とコード照合を担当。Workerが認証結果を検証し、WARA側の暗証番号・会員・セッションを扱う。現行公開設定はGoogle。Twilioは別モード。 |
| 組み込み・紙の財布／Phantom | Worker＋D1、またはPhantom | 組み込み・紙の財布の鍵は暗号化して保管しWorkerで署名。Phantomを選んだ人はPhantomで本人署名する。手数料支援の有無と、本人がどこで署名するかは別の選択。 |
| 日次INA枠・地域別WARA残高・市場の一覧 | ブラウザ → Solana公式公開RPC／予備のOnFinality公開RPC → Devnet | 日次使用量、トークン口座、地域・公認店・参加状態を読む。市場の一覧では残高の照会を省く。 |
| 限定公開コミュニティの改名・参加者への表示 | Worker＋D1＋認証付きOnFinality | 表示名は暗号化してD1に保存。Workerが管理者・参加資格を台帳と照合する。確認済み資格は一定時間再利用する。**名前だけの保存には台帳取引も招待リンクの再発行も不要。** |
| 店舗申請・公認・プロフィール、コミュニティ参加・提携 | Worker＋D1＋OnFinality、ブラウザとDevnet | 店舗の申請や紹介文・アイコンはD1。公認店・会員資格・提携の効力は台帳に記録する。申請を受け付けた段階と、公認の取引が確定した段階を分ける。 |
| 決済の署名前検査・手数料支援・送信 | Worker＋Helius＋Devnet、D1 | Workerの決済専用口は `DEVNET_PAYMENT_RPC_URL`。D1は重複受付の処理と状態照会に使う。支援財布にはDevnet SOLが必要。支援を使わない直接送信はブラウザのRPCを通る。 |
| 店頭QR・入金表示・取引履歴 | QRの読み取りは端末内。入金の確認はブラウザ → 公開RPC。個別照合はSolana Explorer | QRを読めたことは支払い完了を意味しない。店のレジを開いたまま新着を検知する機能と、後から財布の履歴を見る機能は別々に試す。 |
| 地域WARAの名前・画像を外部の財布に見せる | Solana Devnet上のMetaplexメタデータ、Worker＋OnFinality、同サイトの画像 | 新しい地域のトークン情報はWorkerが台帳を確認して配信。限定公開の参加者向け表示名とは別の公開情報。 |
| 開発版の保存と検査 | GitHub・GitHub Actions、配備先はCloudflare Workers | GitHubはコードの履歴とCIの場所。利用者が支払うたびには呼ばれない。本番版との対応は下の完了項目を参照。 |

**「閲覧用OnFinality」はWorkerの閲覧用**（`DEVNET_RPC_URL`）。利用者のブラウザにはどちらのサービスの秘密URLも渡さない。ブラウザの予備もOnFinalityだが、こちらは鍵なしの公開口で、Worker用の契約枠とは異なる。HeliusのAPIキーとキー入りRPC URLは同じ接続の認証情報で、第三の経路ではない。今の専用決済経路にTatumが自動で加わることもない。

## 困ったとき、どこから見るか

| 症状 | 最初の確認 |
| --- | --- |
| 登録SMSが来ない | Firebaseの電話認証・SMS枠とWARA側の送信制限。決済用RPCの使用量を見てもこの症状は分からない。 |
| 限定公開の名前だけ古い・「名称未確認」 | D1の保存版、Workerの参加資格照合、OnFinalityの閲覧応答。管理者が保存できた時刻と、参加者が更新した時刻を分けて見る。 |
| 支払いが「確認中」 | まず元の取引を照合する。署名があればDevnetの取引結果、まだなければWorkerのリレー受付を確認。元の成否が分かるまで新たな支払いは作らない。 |
| 買い手は完了、店には出ない | 同じ署名で台帳の宛先と増加額を確認。店に＋90があれば、送信は完了。店主の財布・選択店舗が合っているか、公開RPCから履歴・新着を取得できたかを調べる。 |
